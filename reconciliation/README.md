# Process Catalog Reconciliation (CR-BP-15-IMP)

**CR-BP-15-IMP Phases 1-4 (this PR + previous); CR-BP-15 §6 / §7.**

The reconciliation directory hosts the artefacts that drive
CR-BP-15-IMP Phases 1-7: the inventory of every canonical record
as-at CR-BP-14 implementation, the immutable baseline that freezes
those records, the per-record disposition register, the tranche
plan, and the per-tranche diffs that CR-BP-15-IMP Phases 5-7
introduce.

## Layout

```
reconciliation/
├── README.md                         # this file
├── inventory.yaml                    # per-record metadata + raw findings
├── baseline/
│   └── v1.yaml                       # immutable SHA-256 snapshot
├── dispositions/                     # CR-BP-15-IMP Phases 3..4 (this PR)
│   ├── schema.yaml                   # canonical disposition schema
│   └── register.yaml                 # per-record disposition decisions
├── tranches/                         # CR-BP-15-IMP Phases 3..4 (this PR)
│   └── plan.yaml                     # 10 Process-Context tranches
└── diffs/                            # CR-BP-15-IMP Phases 5..7 (later PRs)
    ├── phase-5.yaml
    ├── phase-6.yaml
    └── ...
```

`reports/` (top-level) hosts machine-readable reconciliation
reports generated by `scripts/build_inventory.py` and future
tranche scripts.

## Phase 1: inventory (PR-31)

`reconciliation/inventory.yaml` enumerates every record in the
canonical catalog at the moment CR-BP-14 was declared Implemented:

- 18 Business Processes (L2);
- 10 Process Groups (L1);
- 10 Process Contexts;
- 4 Change Requests (CR-BP-14, CR-BP-15, CR-BP-15-IMP, CR-BP-16).

Each record carries `id`, `name`, `type`, `path`, the legacy
findings (raw BP-SEM findings on that record), and (where
applicable) `process_intent` and `process_classification`.

## Phase 2: baseline (PR-31)

`reconciliation/baseline/v1.yaml` is the immutable snapshot that
freezes the canonical catalog at the same moment. Every record
carries `id`, `type`, `path`, and a `sha256` of the file's bytes
at baseline time.

## Phase 3: disposition schema + register (this PR)

`reconciliation/dispositions/schema.yaml` declares the 9 canonical
dispositions from CR-BP-15 §28: RETAIN, RECLASSIFY, RENAME,
SPECIALIZE, MERGE, SPLIT, MOVE, DEFER, RETIRE. Each disposition
specifies the required fields and the rationale pattern.

`reconciliation/dispositions/register.yaml` records the preliminary
disposition decision for every Business Process (18 entries). The
register is **PRELIMINARY**; it will be LOCKED during
CR-BP-15-IMP Phase 5 (PR-6 onward). At this stage, all 18
dispositions are RECLASSIFY because every record carries legacy
vocabulary tokens that migrate to the canonical forms via
CR-BP-14 §17's mapping.

The register covers the four documented legacy findings on every
record:

1. legacy `process_intent` vocabulary (`operational`, `support`,
   `management`) migrates to the canonical 7-value vocabulary
   (`govern`, `manage`, `operate`, `deliver`, `support`,
   `develop`, `transform`) per CR-BP-14 §17 evidence-based
   mapping;
2. legacy scalar `process_context` migrates to the canonical
   `context:` block per CR-BP-14 §13, §20;
3. legacy `process_audience` is removed because the canonical
   `context:` block already declares the ECF Domain x Lifecycle
   placement per CR-BP-14 §13;
4. `process_specialization` remains absent for these 18 records;
   CR-BP-15-IMP Phase 6 will introduce specializations where the
   catalogue narrative supports them.

## Phase 4: tranche plan (this PR)

`reconciliation/tranches/plan.yaml` groups the 18 records into 10
tranches, one per Process Context (ECF Domain x Lifecycle Stage):

| Tranche | Context | Records |
|---|---|---|
| cd-b | customer-demand / build | 2 |
| cd-c | customer-demand / conceive | 2 |
| cd-d | customer-demand / design | 3 |
| cd-im | customer-demand / improve | 1 |
| cd-op | customer-demand / operate | 1 |
| ge-b | governance / build | 2 (high-risk: audience-vs-context) |
| ge-c | governance / conceive | 2 |
| ge-d | governance / design | 2 |
| ge-im | governance / improve | 1 |
| ge-op | governance / operate | 2 (high-risk: cross-tranche references) |

Tranches are independent; the migration order MAY be interleaved
or parallelised. Each tranche maps to one PR in the
CR-BP-15-IMP Phases 5-7 roadmap (PR-6..9).

## Phase 5-7 (future PRs)

CR-BP-15-IMP Phase 5 introduces per-tranche migrations in PR-6..9
(approximately two tranches per PR). Phase 6 introduces
specialization entries where the catalogue narrative supports them.
Phase 7 introduces the per-tranche diffs (which records were
touched, what changed, and how the SHA-256 baseline evolved).

## STRUCT conformance (decision D6)

`scripts/check_struct.py` (PR-31) flags unknown top-level entries
so reconciliation scaffolding typos (e.g. `reconcilliation/`)
cannot shadow a real directory.

## Disposition validator (this PR)

`scripts/check_dispositions.py` validates the disposition register
+ tranche plan against:

- the inventory (every record has exactly one disposition entry);
- the disposition schema (every disposition id is canonical;
  per-disposition required fields are present);
- the CR-BP-14 canonical vocabularies (every RECLASSIFY intent
  target is canonical; every RECLASSIFY context target resolves
  to a registered Process Context);
- the tranche plan (every plan entry references a disposition
  entry).

The validator is wired into CI as an advisory step
(`--strict || true`) until the register is LOCKED in Phase 5.
